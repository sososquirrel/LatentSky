LatentSky Model Reference

The complete recipe for the canonical model pair of the LatentSky paper: the two-head deterministic U-Net and the conditional diffusion model that refines its forecast, trained on the same DYAMOND data, the same ten input channels, and the same leakage-safe patch split, at six lead times from 15 minutes to 6 hours.

1 · Data and preprocessing

Source fields

The dataset is a continuous ~40-day global storm-resolving DYAMOND integration, regridded to a regular 0.25° grid over the tropical belt 40°S–40°N and split into 40 daily "pieces". Each variable is stored as one NumPy file per day, <variable>_piece{00..39}.npy, of shape (96, 320, 1440) float32: 96 frames of 15 minutes (24 h), 320 latitude rows × 1440 longitude columns (≈ 27.8 km meridional grid spacing). Files live in /glade/derecho/scratch/sabramian/latentsky_pieces/ and are memory-mapped at load time.

Input channels and target

Both models take the identical 10 input channels, stacked in this exact order (channel index matters: OLR conditioning and pretraining masks address channels by position):

#ChannelField
0precipwprecipitable water
1t2m2-m temperature
2olrtoaoutgoing longwave radiation, top of atmosphere
3mse_500hPamoist static energy, 500 hPa
4mse_850hPamoist static energy, 850 hPa
5uzonal_500hPazonal wind, 500 hPa
6uzonal_850hPazonal wind, 850 hPa
7umeridional_500hPameridional wind, 500 hPa
8umeridional_850hPameridional wind, 850 hPa
9rain_log1pz-scored log1p of current rain — the persistence forecast as an input (see Standardization)

The target is rain_total (mm) at the requested lead, a single channel. The rain_log1p input is a deliberate design choice, not leakage: every model receives the persistence forecast as one of its channels, so the persistence null is nested — any skill above persistence is information the model added. Other variables exist in the piece store (relhum, temperature, w at 500/850 hPa) but are not used by the canonical models.

Standardization

The training code applies no normalization — but the piece files are already standardized upstream, in the piece-creation pipeline (verified 2026-09-02 from the files themselves, not the code):

  • The nine met input channels are globally z-scored (dataset-wide constants, not per-day: per-piece means are ≈0 but not exactly 0, e.g. t2m mean −0.011/+0.008/−0.013 on pieces 00/20/35). Sample stats on piece 00: t2m ranges −7.4…3.0 with std 1.05; olrtoa is the one channel with std ≠ 1 (0.40).
  • The rain input is a z-scored log-transform: rain_log1p = (log1p(rain_total) − 0.023456) / 0.118232, exact to 2×10⁻⁶ (equivalently 8.458013·log1p(rain) − 0.198390). Dry pixels sit at −0.19839, not 0.
  • The target is raw: rain_total in mm, min 0, piece-00 max 23.7 mm. Only the diffusion trainer transforms it (§4).
Reproducibility gap. The upstream standardization constants for the nine met channels are baked into the piece files and not recorded in this repository; the rain constants above were recovered empirically (least-squares fit of rain_log1p against log1p(rain_total), residual < 2×10⁻⁶). Rebuilding piece files from raw DYAMOND output requires recovering the met-channel constants the same way — or retraining is insensitive to them as long as inputs are z-scored consistently. Anyone using the trained checkpoints must feed identically standardized inputs.

Lead-time construction

A lead is specified as lead_steps_15, the number of 15-min frames (1 h lead = 4). Inputs and targets are paired by a time slip of delta_index = lead_steps_15 + 1 frames: X[0 : T−δ] pairs with Y[δ : T]. The +1 corrects a known one-frame offset in the raw piece files (raw X[i] is simultaneous with raw Y[i+1]); the effective physical lead is lead_steps_15 × 15 min. Six leads are trained per family: 0.25, 0.5, 1, 2, 3, 6 h (steps 1, 2, 4, 8, 12, 24).

Patch tiling

Training samples are 128 × 128 non-overlapping patches tiled from each frame: a 2 × 11 grid of 22 blocks per frame (320 // 128 = 2, 1440 // 128 = 11). The remainder — the last 64 latitude rows and 32 longitude columns — is excluded from training and, by the same convention, left at zero in tiled inference. Batches are 64 patches; each patch carries all 10 channels.

2 · Train / val / test split

Both model families use the identical patch-level split. The split unit is a block (piece, row, col) — one 128-px tile location on one day, kept together across all 96 frames of that day. The 40 × 22 = 880 blocks are shuffled with random.Random(1919810) and cut 70 / 15 / 15 → 616 train, 132 val, 132 test blocks. Two properties make this leakage-safe:

  • Blocks never overlap (stride = patch size), so no pixel appears in two splits.
  • All frames of one block stay in one split, so 15-min temporal autocorrelation cannot leak across splits at a fixed location.

The accepted residual risk: a storm straddling the border of two adjacent blocks assigned to different splits. Evaluation restricts object statistics to systems whose centroid falls in a held-out test block (patch_split.restrict_to_patch_test_blocks).

Manifest pitfall. The diffusion run manifests record split_mode: "piece". That field is an unused config default: train_diffusion.py ignores it and always builds the patch split above with the same seed and fractions. Both families are on the identical split; trust the code path, not the manifest field.

One epoch visits the 40 pieces in a shuffled order (random.Random(seed + epoch)); each piece is read from disk once and contributes its train-assigned and val-assigned patches in the same pass.

3 · Deterministic model two-head U-Net

Architecture — UNet2DTwoHead

Input / output10 channels, 128×128 → rain field (mm) + wet/dry logit field
Encoder5 stages of DoubleConv (two 3×3 conv → GroupNorm → ReLU → Dropout2d 0.05), channels 64 → 128 → 256 → 512 → 1024, MaxPool 2× between stages
BottleneckDoubleConv to 2048 channels at 4×4
OLR-FiLM conditioningper-patch [mean(OLR), min(OLR)] from input channel 2 → MLP (2 → 64 → 4096) → (γ, β) affine modulation of the bottleneck feature map — a convective-regime gate (cold-top/deep vs warm/shallow), motivated by the 2026-07 regime diagnostic
Decoder5 stages: ConvTranspose2d (kernel 2, stride 2) up, concat skip, DoubleConv back down to 64
NormalizationGroupNorm, 8 groups (reduced to divide the channel count), conv bias off
Output headstwo parallel 1×1 convs: rain_head → Softplus (β = 1, threshold 20), non-negative mm; wetdry_head → raw logits for BCEWithLogitsLoss
Parameters124.6 M

Loss

A three-term combined loss, total = mse + 1.0·bce + 0.25·fss:

  • Masked intensity MSE — MSE(rain_pred[mask], y[mask]) with mask = y_true > 0, in raw mm: intensity is supervised on wet pixels only.
  • Wet/dry BCE, weight 1.0 — BCEWithLogitsLoss on the classification head over the full field, dry pixels included. This is what makes the two-head trainable on the whole domain, unlike a plain masked-MSE model that never receives a gradient from dry pixels.
  • Multi-scale FSS term, weight 0.25 — a differentiable fractions-skill-score loss at kernel sizes [1, 3, 5, 11, 19, 33] px (derived from the paper's own L = √A scale bins at 27.8 km/px), wet threshold 0.1 mm, sigmoid sharpness 20 — penalizes misplaced rainy fractions at each analysis scale.

Validation losses below are this combined total and are not comparable to the plain masked MSE of the one-head variant.

4 · Diffusion model conditional DDPM

Target transform

The diffusion state is not rain but x₀ = log1p(rain_total) / 2.0 — roughly unit range (a 22 mm event maps to x₀ ≈ 1.6). Samples are inverted with rain = expm1(2.0 · x₀). Unlike the deterministic loss there is no wet-pixel masking: the ε-loss covers the whole field, so the diffusion model does train on dry pixels.

Architecture — ConditionalDiffusionUNet

Inputnoisy target xt (1 ch) ⧺ the 10 conditioning channels = 11 channels, 128×128
Backbonesame DoubleConv encoder–decoder as UNet2D: depth 5, base 64, bottleneck 2048, GroupNorm(8), dropout 0.05
Time conditioningsinusoidal embedding of t (dim 128) → MLP to 512, then per-level FiLM: a Linear per encoder stage, bottleneck, and decoder stage produces (γ, β) that modulate the feature map after each DoubleConv
Output1×1 conv → predicted noise ε̂, no activation
Parameters130.9 M

Forward process and loss

Standard DDPM with T = 1000 timesteps on the cosine schedule (Nichol & Dhariwal 2021; β clipped to [10⁻⁴, 0.999]). Per batch: draw t ~ U{0, …, 999} per sample, noise x_t = √ᾱ_t·x₀ + √(1−ᾱ_t)·ε, and minimize MSE(ε̂(x_t, cond, t), ε).

Training schedule

Identical to the deterministic schedule except the learning rate: AdamW(lr=2e-4, weight_decay=1e-5), StepLR(8, 0.5), batch 64, patch 128, ≤ 155 epochs, patience 10, seed 1919810, best-val checkpointing, single GPU.

5 · What the diffusion model adds

Both models share the trunk of §3 and see the same ten standardized channels; the difference is what they are asked to produce. The deterministic model's intensity head minimizes MSE, so it returns the conditional mean of an increasingly wide predictive distribution — as lead grows, that mean is a blurred, spread-out field that under-represents small scales and peak intensity (the mechanism behind the compensating area/intensity errors of R2, and behind the unbounded growth of matched-system position error); the BCE and FSS terms sharpen detection but do not change what the intensity head estimates. The diffusion model learns the full conditional distribution and returns sharp samples from it, at the price of stochasticity and ~300× the inference cost.

Inference: refinement, not replacement

The canonical evaluation does not sample from pure noise. It uses SDEdit-style warm-started ancestral sampling (GaussianDiffusion.ddpm_refine_sample), per 128-px tile, per frame — the deterministic forecast supplies the large-scale answer and the diffusion chain restores the small-scale structure the conditional mean lost:

Rationale and cost: warm-starting takes the "is it raining, roughly how much" structure from the independently validated regression and bounds compounding drift to t_start + 1 = 101 network evaluations per draw (vs 1000 from pure noise). Pure-noise ancestral sampling and DDIM both exist in the code; DDIM's x₀-parameterization is numerically unstable at high noise (≈ 2×10⁴ error amplification near t = 999), which is why the posterior-mean form is used. A t_start sweep on bulk pixel metrics degraded R² from 0.39 (t_start = 50) to 0.31 (t_start = 400); production uses t_start = 100, ensemble = 3 (the per-frame prediction API defaults to 150 / 5 — the evaluation entry point overrides them). The per-step x₀ clamp to (0, 2.5) is a hard physical floor (rain ≥ 0) plus a generous ceiling (≈ 147 mm) set from the training-data x₀ distribution.

Warm-start source. Per the paper frame, the canonical warm start is the two-head run at the same lead (patchsplit_twohead_olr_fss_lead*) — which is also the code default for regression_run_name. Passing the one-head run instead (patchsplit_onehead_lead*) gives the oneheadbackbone sensitivity variant.

6 · Step-by-step reproduction

  1. Environment. Python 3.11, PyTorch 2.6.0+cu124, NumPy 2.4.3, one NVIDIA A100. On Derecho: conda env at /glade/work/sabramian/conda-envs/latentsky-env, with the env's bundled NVIDIA libraries on LD_LIBRARY_PATH (see the repo Makefile or experiments/_template/job.sh).
  2. Data. Piece files for the 10 input variables plus rain_total, named <var>_pieceNN.npy, shape (96, 320, 1440) float32, in one directory (pieces_dir). Inputs must be standardized as described in §1 — the met channels globally z-scored, the rain input as (log1p(rain) − 0.023456)/0.118232, the target raw mm — because the trained checkpoints expect exactly those scales.
  3. Config. One YAML per run. The canonical deterministic config, in full: 
    name: patchsplit_twohead_olr_fss_lead1h
input_vars: [precipw, t2m, olrtoa, mse_500hPa, mse_850hPa,
             uzonal_500hPa, uzonal_850hPa, umeridional_500hPa,
             umeridional_850hPa, rain_log1p]
lead_steps_15: 4          # 1 h; use 1,2,4,8,12,24 for the six leads
target_prefix: rain_total
two_head: true            # false → the one-head sensitivity variant
olr_var_name: olrtoa
bce_weight: 1.0
fss_weight: 0.25
fss_threshold: 0.1
fss_sharpness: 20.0
fss_max_kernel_px: 33
base_ch: 64
depth: 5
dropout_p: 0.05

num_epochs: 155
patience: 10

weight_decay: 1.0e-5
lr_step: 8
lr_gamma: 0.5

split_mode: patch         # read by train.py; train_diffusion.py always patch-splits

  4. Train. python -m latentsky.train --config configs/<name>.yaml for the deterministic model, python -m latentsky.train_diffusion --config … for the diffusion model. Each run writes manifest.json (full config + git SHA + loss history), checkpoint.pt (best-val weights), train.log, and loss.png. Wall clock on one A100: hours per run (12 h queue allocation was sufficient for every run including the 84-epoch one).
  5. Verify. The repo's tests/test_models.py loads both canonical checkpoints with load_state_dict(strict=True) — an architecture that key-matches those checkpoints is the architecture described here.
  6. Predict. Deterministic: one forward pass per 128-px tile; the model returns (rain, wet/dry logits) and the rain head, in mm, is the forecast. Diffusion: the warm-started sampler of §5 with t_start = 100, ensemble 3, conditioned on the same 10 channels.
